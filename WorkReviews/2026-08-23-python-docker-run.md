# Отчёт о работе: Python-проект через Docker

- Дата: 2026-08-23
- Статус: реализация завершена; реальный Docker build ожидает доступный daemon
- Этап плана: Фаза 1, первый вертикальный срез

## Результат

Реализована команда:

```bash
hostix run <project>
```

Она определяет Python-проект, выбирает безопасную команду запуска, создаёт
временный Docker build context, собирает образ, идемпотентно заменяет предыдущий
Hostix-контейнер и запускает новый.

## Выполненные задачи

### Определение проекта

- Python определяется по `requirements.txt` и `pyproject.toml`.
- Поддерживаются зависимости PEP 621 и Poetry.
- Определяются типовые FastAPI, Flask и Django entrypoint.
- Код проекта при анализе не исполняется.
- Конфликтующие framework/entrypoint возвращают понятную ошибку.
- Неоднозначность можно разрешить явной командой после `--`.

### Генерация образа

- Базовый образ: `python:3.12-slim`.
- Команда записывается в безопасной JSON exec-форме `CMD`.
- Контейнер запускается не от root-пользователя.
- Пользовательский `Dockerfile` не изменяется.
- Hostix создаёт `.hostix.Dockerfile` только внутри временного TAR-архива.
- Временный архив удаляется после сборки, включая ошибочные сценарии.
- Поддерживается консервативное подмножество `.dockerignore`, включая порядок
  правил, `!`, `*`, `?`, классы символов и `**`.
- `.env` и `.env.*` всегда исключаются из build context; `.env.example`
  разрешён.

### DockerRuntime

- Реализованы `Create`, `Start`, `Stop`, `Remove`, `Exec`, `Logs`, `Status` и
  `List`.
- Реализована сборка образа с обработкой асинхронного потока Docker build.
- Используются поддерживаемые модули `moby/moby/client` и `moby/moby/api`.
- Ошибки SDK преобразуются в общие `ErrNotFound` и `ErrAlreadyExists`.
- Логи и exec-потоки корректно демультиплексируются и закрываются.
- `List` возвращает только ресурсы с Hostix ownership label.

### Оркестрация и безопасность

- Имя контейнера и image tag детерминированы по каноническому пути проекта.
- Повторный запуск не создаёт дубликаты.
- Существующий контейнер удаляется только после успешной сборки нового образа.
- Контейнер с совпавшим именем, но без Hostix ownership label, не удаляется.
- Неудачно стартовавший новый контейнер очищается автоматически.
- Для распознанных web-framework по умолчанию публикуется `8000:8000`.

### CLI

Добавлены флаги:

- `--stack auto|python`;
- `--runtime auto|docker`;
- `--name`;
- `--port HOST:CONTAINER[/PROTOCOL]`;
- `--env NAME=VALUE`.

Явная команда запуска передаётся так:

```bash
hostix run . -- python main.py
```

### Диагностика

`hostix doctor` теперь различает установленный Docker CLI и доступный Docker
daemon. Это устраняет ложный статус готовности, когда бинарник Docker найден,
но engine не запущен.

## Ограничение проверки окружения

На текущем хосте Docker CLI `29.5.2` установлен, но Docker daemon недоступен и
приложение Docker Desktop отсутствует. Поэтому реальная загрузка
`python:3.12-slim`, сборка образа и запуск контейнера на этом хосте не
выполнялись. Hostix корректно диагностирует это состояние и завершает команды с
понятной ошибкой. Интеграционные тесты с настоящим daemon остаются отдельной
незавершённой задачей Фазы 1.
